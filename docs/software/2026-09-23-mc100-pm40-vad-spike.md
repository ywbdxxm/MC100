# MC100 Phase 1：PM40 / VAD 实板 Spike 报告

> **报告日期：** 2026-09-23
> **阶段门禁：** **OPEN（部分证据已取得，不能关闭）**
> **结论摘要：** 在本项目锁定的 ESP-IDF v6.1 / ESP32-S3-MINI-1-N8（无 PSRAM）组合上，连续 PDM RX 在固定 CPU/APB 40 MHz 配置下未能完成 `i2s_channel_enable()`；固定 80 MHz 可以连续运行。DFS 的最低频率虽然设为 40 MHz，但 PDM 活跃时实际 CPU/APB 为 80/80 MHz。因此“PDM + VAD 全程 40 MHz”目前不成立。esp-sr 2.4.7 的 VADNet1 medium 已完成**无 PSRAM target build**，并已在 COM7 完成模型分区加载与 VAD 配置探针；但 AFE 创建在 `SR_RINGBUF` 分配处因内部内存耗尽而失败并触发 panic，未得到帧级运行数据。该结果只约束本模型/配置/无 PSRAM tuple，不能外推为所有 esp-sr 配置均不可行；授权语料、电流和公平 VAD 对比仍未完成，VAD 仍不选型。

本报告记录 2026-09-23 的 PM/VAD 可行性实验。`firmware/spikes/pm40_vad/` 是一次性测量程序，不是产品运行时；报告中的构建、Flash 和监控证据均只针对用户授权的 **COM7**，没有操作其它串口。当前任务状态见[验证与状态](../MC100-VALIDATION.md)。

## 3. PM/PDM 结果

| 运行 | PM 配置后实际时钟 | PDM 启动/持续读取 | 10 秒统计 | 结论 |
| --- | --- | --- | --- | --- |
| 固定 40 | `CPU=40 MHz`, `APB=40 MHz` | 打印 `PDM_INFO` 后，`i2s_channel_enable()` 未返回；没有 `PDM_START result`、进度或 summary | 约 10.093 s 起触发 Task WDT；反复同一回溯 | **失败：固定 40 的 PDM RX 启动路径卡死** |
| 固定 40 + APB lock | 仍为 `CPU=40`, `APB=40`；`PROBE_APB_LOCK result=0 held=1` | 与固定 40 相同，仍在启动阶段卡住 | Task WDT；无帧 | **失败：额外 lock 不能突破 40 MHz 配置上限** |
| 固定 80 | `CPU=80 MHz`, `APB=80 MHz` | `PDM_START result=0`；连续读满 | `frames=501`, `bytes=320640`, `timeouts=0`, `errors=0` | **通过本次 10 s 连续性探针** |
| DFS（max 80 / min 40） | 初始及 PDM 活跃期间均为 `CPU=80`, `APB=80` | `PDM_START result=0`；连续读满 | `frames=501`, `bytes=320640`, `timeouts=0`, `errors=0` | **PDM 可运行，但活跃期间不是 40 MHz** |

四种配置的 PDM 时钟参数均记录为 `sclk_hz=160000000`、`bclk_hz=1024000`、`mclk_hz=8192000`、DMA 总字节数 3840。固定 40 日志确实完成了 PDM 配置和 `PDM_INFO` 打印，失败发生在启用通道之后，不是“没有烧录”或“没有识别麦克风”。

### 3.1 固定 40 的故障定位

使用与 ESP-IDF v6.1 构建匹配的 `xtensa-esp32s3-elf-addr2line` 解码 WDT 回溯，核心帧为：

```text
i2s_ll_rx_update       esp_hal_i2s/.../i2s_ll.h:466
i2s_ll_rx_start        esp_hal_i2s/.../i2s_ll.h:489
i2s_rx_channel_start   esp_driver_i2s/i2s_common.c:292
i2s_channel_enable     esp_driver_i2s/i2s_common.c:1489
start_pdm              firmware/spikes/pm40_vad/main/pm40_vad_probe.c:88
run_probe              firmware/spikes/pm40_vad/main/pm40_vad_probe.c:166/179
```

`i2s_ll_rx_update()` 在 IDF v6.1 的实现是写入 `rx_update` 后等待该位清零的 busy-wait。与该回溯对应的 `components/esp_pm/pm_impl.c:460-469` 逻辑为（ESP32-S3 分支）：

```c
apb_max_freq = MIN(max_freq_mhz, apb_clk_freq);
apb_max_freq = MAX(apb_max_freq, min_freq_mhz);
```

所以在 `max_freq_mhz=40`、`min_freq_mhz=40` 时，PM 的 APB_MAX 仍被限定为 40 MHz；显式 APB lock 只报告 acquire 成功，不能把已配置的上限提高到 80 MHz。这个源码约束、实际 `CPU/APB=40/40` 和 `rx_update` 回溯相互吻合。报告将其记为“当前 SDK/配置下的 PDM 启动不兼容”，不外推到其它 IDF 版本、其它 I2S 模式或其它芯片。

## 4. libfvad 工程探针（不是选型结论）

libfvad 在无 PSRAM 的目标上成功初始化：

```text
VAD_INIT ptr=1 mode_result=0 rate_result=0
heap_before=380472 largest_before=319488
heap_after=379700 largest_after=319488
```

这里的初始化前后差值是约 772 bytes 内部堆；`largest_before/after` 均为 319488 bytes。固定 80 和 DFS（PDM 活跃时 80 MHz）均对 501 个 20 ms 帧执行了 `fvad_process`：

| 运行 | VAD 帧 | `vad_speech` | 最小 / 平均 / P95 / 最大（µs） | summary |
| --- | ---: | ---: | ---: | --- |
| 固定 80 | 501 | 4 | 389 / 394 / 402 / 638 | `05-monitor-pm80.stdout.log` |
| DFS（requested 40，实际 80） | 501 | 4 | 389 / 394 / 401 / 644 | `11-monitor-pm40-dfs.stdout.log` |

`vad_speech=4` 仅是本轮板上环境输入的二值输出计数，不能解释为召回率、误启动率或人声质量。固定 40 因 PDM 未启动，没有可比的 VAD 运行数据。

## 5. esp-sr VADNet target build 与运行时探针

使用独立的 Component Manager throwaway 工程构建 `espressif/esp-sr==2.4.7`，目标为 `esp32s3`，关闭 PSRAM（生成的配置没有 `CONFIG_SPIRAM`），并启用 `CONFIG_SR_VADN_VADNET1_MEDIUM=y`。探针代码把 AFE 内存策略设为 `AFE_MEMORY_ALLOC_MORE_INTERNAL`。Windows 长路径会使 GCC 无法创建依赖文件，因此构建使用了短的临时物理路径；源代码和完整日志仍保存在被忽略的 probe/evidence 目录。

结果：**target build PASS**。Component Manager 解析 esp-sr 2.4.7 及 cjson 1.7.19~2、dl_fft 0.7.0、esp-dsp 1.8.0；模型报告为 `vadnet1_medium` 281.16 KiB；生成 ESP32-S3 镜像 `mc100_esp_sr_probe.bin`（0x846a0 bytes），3 MiB app 分区剩余 83%。完整日志和生成物保存在本地忽略的 `firmware/out/phase1-evidence/`；该目录不属于版本库，缺失时不能作为可复核仓库证据。日志中的 Kconfig `default False` 提示来自上游 esp-sr/IDF 配置解析，未阻止构建。

本结果只证明“无 PSRAM 的 ESP32-S3 target image 可构建”。随后用该镜像在 **COM7** 做了运行时探针，得到：

```text
SR_PROBE_START target=esp32s3 spiram_config=0
SR_HEAP phase=before_models internal_free=384368 internal_largest=319488 spiram_free=0
SR_MODEL_INIT result=OK count=1
SR_MODEL index=0 name=vadnet1_medium
SR_AFE_CONFIG checked vad_init=1 vad_model=vadnet1_medium memory_mode=1 pcm_channels=1 mic=1 rate=16000
SR_HEAP phase=before_afe internal_free=383384 internal_largest=319488 spiram_free=0
SR_RINGBUF: sr_rb_create: Memory exhausted
Guru Meditation Error: Core 0 panic'ed (StoreProhibited)
```

**运行时状态：INIT FAIL / BLOCKED。** 未出现 `SR_AFE_CREATE` 成功、每帧处理或 PDM-fed 统计。回溯为 `flash_model_info` → `model_create` → `afe_init_vad` → `afe_create_from_config` → `app_main`；完整重复日志位于本地忽略的 `firmware/out/phase1-evidence/`。这是本次 `vadnet1_medium`、无 PSRAM、`AFE_MEMORY_ALLOC_MORE_INTERNAL` 配置的内部内存门禁失败，不足以断言其它 esp-sr 模型或内存策略不可行。实验前的 8 MiB Flash 备份为 `esp-sr-runtime-before-20260923.bin`（SHA-256 `82D4D76EC9D3ADC83BEAFBC14C4310DCF1870D26ABC97C8F48458F99FAF80E8E`）；运行结束后未恢复或再烧录其它镜像，板子保留在 probe 镜像的重启状态。

## 7. Phase 1 决策和后续动作

1. 对本项目的精确 tuple，**不能放行“固定 CPU/APB 40 MHz 连续 PDM + VAD”**。删除 PM lock 或把请求频率写成 40 都不能构成证据。
2. DFS `80/40` 只能作为“允许空闲最低 40 MHz、PDM 活跃回到 80 MHz”的候选策略；它不满足全程 40 MHz 命题，功耗必须等实测电流后再评估。
3. libfvad 已证明“在 80 MHz 路径上可初始化并处理 16 kHz/20 ms 帧”；esp-sr 已证明“无 PSRAM target image 可构建”，但本次 `vadnet1_medium` AFE 创建因内部内存耗尽而 **INIT FAIL / BLOCKED**。这不是对其它 esp-sr 配置的普遍否定；仍需评估可行的模型/内存策略，之后才能做同口径资源/延迟比较和授权语料评估。
4. 在上述缺口完成前，Phase 1 gate 保持 **OPEN**，最终设计 §4 的功耗估算和 §8 的风险项不得改写为已验证；Phase 2 的占位 VAD 也不能被本报告替换成正式 VAD。
